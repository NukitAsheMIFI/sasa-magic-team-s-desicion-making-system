## 1. Описание решения
Многопользовательский аналитический веб-сервис для автоматизированного аудита и сравнения двух версий кредитных стратегий системы принятия решений (СПР): промышленной `BEFORE (MASTER)` и тестируемой релизной версии `AFTER (BETA)`.

Сервис позволяет риск-аналитикам, владельцам продукта и кредитному комитету в сжатые сроки выявить последствия правок стратегии до вывода в промышленную эксплуатацию:
- **Универсальный парсер произвольной вложенности (глубина $4+$):** рекурсивный разбор древовидных JSON-ответов СПР (DFS) с сохранением сквозных путей и составных ключей массивов без привязки к жёсткой схеме.
- **Двухконтурная аналитическая витрина:** формирование детального слоя сравнения на уровне каждого атрибута (`mart_rows`, $290\,842$ строки) и слоя клиентских разрезов (`segments`, $2002$ строки).
- **Сквозной бизнес-вердикт и Net Approval Impact:** автоматический расчёт сдвига уровня одобрения (Approval Rate), динамики кредитного портфеля ($+112$ новых одобрений / $-273$ потерянных) и финансовой ёмкости одобренных лимитов.
- **Альтернативное мнение от ИИ (`RiskCopilot`):** встроенный модуль генерации экспертного управленческого резюме (Executive Summary) для кредитного комитета на основе бизнес-вердикта и результатов проверок без галлюцинаций.
- **Расширяемый движок автопроверок (`MartAPI`):** подключение аналитических правил по принципу Plug-and-Play через стандартный фасад из 5 методов, а также создание и редактирование пользовательских проверок на Python прямо в браузере.
- **Интерактивная сводная таблица (Pivot):** работа поверх предрассчитанных агрегатов `counts` (`pivot_facts`) для мгновенной перестройки срезов со сквозной детализацией (drill-down) от цифры до конкретной заявки и атрибута.
- **Экспорт в HTML:** генерация компактного автономного отчёта по ссылке с умной группировкой длинных списков заявок и бесшовным переходом обратно в веб-интерфейс приложения.
- **Многопользовательский режим:** авторизация по логину, полная изоляция пользовательских конфигураций и результатов прогонов по `user_id`, сохранение состояния при перезагрузке страницы (`F5`).

## 3. Используемые технологии
- **Архитектура «Универсального движка»:** бэкенд не содержит хардкода под конкретные поля JSON. Вся предметная логика (имена полей, правила сравнения, бизнес-проверки) вынесена в пользовательские Python-скрипты, которые исполняются динамически через `subprocess` и `importlib`.
- **Аналитическое ядро и обработка данных:** Python 3.11, Pandas, NumPy (векторные операции `np.select`), PyArrow, рекурсивный обход графов (DFS).
- **Бэкенд:** FastAPI, Uvicorn, SQLAlchemy, Pydantic, асинхронное выполнение фоновых задач (`BackgroundTasks`).
- **База данных:** SQLite3 в режиме `WAL` (Write-Ahead Logging) для параллельного неблокирующего чтения и пакетной записи (`bulk_save_objects`).
- **Интеллектуальный блок (AI):** модуль `RiskCopilot-Hybrid-v1` (`ai_summary.py`) — детерминированный аналитический генератор управленческого резюме с готовым шлюзом под внешние LLM (OpenAI / YandexGPT / GigaChat).
- **Фронтенд:** React 18, Vite, React Router, интерактивная сводная таблица (Pivot), встроенный редактор кода `@uiw/react-codemirror`.
- **Инфраструктура:** Docker, Docker Compose (единый контейнер со сборкой статики фронтенда через Multi-stage build), Bash.

## 4. Данные
- **Источник:** выданный датасет `src/data/RUN-20260827-0001/`, содержащий ответы СПР по **$2002$ кредитным заявкам** в двух срезах:
  * `BEFORE_MASTER` — $2002$ JSON-файла (текущая промышленная стратегия);
  * `AFTER_BETA` — $2002$ JSON-файла (тестируемая стратегия с изменениями).
  Суммарный объём — $4004$ файла ($\sim 20$ МБ).
- **Структура входа:** имя файла соответствует идентификатору заявки (`APP_ID`) и выступает ключом сквозного сопоставления. Каждый ответ содержит от $131$ до $178$ атрибутов со сложными ветвлениями, вложенными списками предложений (`available_offers`) и массивами правил (`product_trials.rules`).
- **Этапы конвейера предобработки данных:**
  1. *Нормализация (`normalize.py`):* рекурсивный спуск (DFS) разбирает иерархические структуры произвольной глубины ($4+$). Первый уровень формирует `PREFIX`, второй — `CLASS`, терминальный ключ — `KEY`, промежуточные уровни упаковываются в `SUFFIX`, а идентификаторы элементов списков объединяются в составной `ARRAY_KEY`.
  2. *Вертикальный UNION и сопоставление (`compare.py`):* объединение срезов с меткой `SOURCE` и последующий Full Outer Join по составному ключу `(APP_ID, PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY)` с векторизованной разметкой 4 типов изменений (`SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`) в витрину на $290\,842$ строки.
  3. *Выделение слоя разрезов (`segments`):* извлечение по каждой из $2002$ заявок 8 ключевых бизнес-параметров (`DECISION_BEFORE`, `DECISION_AFTER`, `PRODUCTS`, скоринговые модели и пороги).
  4. *Предрасчёт агрегатов (`pivot_facts`):* группировка фактов `counts` на этапе конвейера для мгновенной отдачи данных в сводную таблицу.

## 5. Архитектура и подход

1. **Асинхронный неблокирующий конвейер и прозрачный журнал этапов:**
   * Тяжёлые вычисления выполняются в фоновом потоке, а статус каждого шага (`load` $\to$ `normalize` $\to$ `checks`) фиксируется в таблице `run_steps` с таймстампами начала и окончания.
   * Пользователь в реальном времени видит прогресс выполнения и может перейти из журнала этапов к коду исполняемой процедуры.
   * Благодаря хранению состояния в SQLite приложение полностью устойчиво к обновлению страницы (`F5`).

2. **Универсальность парсера (глубина $4+$):**
   * Отказ от жёстко заданных путей позволил обрабатывать вложенные структуры любой сложности без модификации кода движка при изменении схемы данных на стороне банка.

3. **Контрактная архитектура `MartAPI` (Plug-and-Play для проверок):**
   * Все проверки изолированы от прямых SQL-запросов и работают через фасад `MartAPI` (`mart.py`), предоставляющий 5 стандартизированных методов:
     * `mart.rows(**filters)` — выборка строк детальной витрины;
     * `mart.count(**filters)` — быстрый подсчёт количества строк;
     * `mart.app_ids(**filters)` — получение уникальных `APP_ID`;
     * `mart.segments()` — доступ к витрине клиентских разрезов;
     * `mart.total_apps()` — общее число заявок в прогоне.

4. **Авторская финансовая бизнес-проверка (`check_product_rule_impact.py`):**
   * Помимо 5 базовых проверок, реализован финансовый модуль, который находит заявки со сменой решения на `APPROVE`, сопоставляет их со сработавшими правилами (`rules.hit`) и считает суммарный денежный объём выданных кредитных лимитов (`limitResult.limit`).

5. **Двухуровневое хранилище данных:**
   * *Быстрый контур (`pivot_facts`, `segments`):* обслуживает дашборд KPI и сводную таблицу за доли секунды.
   * *Детальный контур (`mart_rows`):* запрашивается точечно по индексам только при drill-down переходе к конкретной заявке или атрибуту.

Испытания и замеры проведены на полном выданном датасете `RUN-20260827-0001` ($2002$ заявки, $4004$ JSON-файла).

### Ключевые бизнес-показатели прогона:
- **Объём обработанной выборки:** $2002$ заявки ($4004$ JSON-файла, $290\,842$ строки в итоговой витрине сравнения).
- **Заявок с различиями:** $2002$ из $2002$ ($100\%$ заявок затронуты обновлением скоринговых признаков и параметров).
- **Approval Rate (ДО / MASTER):** $32.82\%$ ($657$ одобренных заявок).
- **Approval Rate (ПОСЛЕ / BETA):** $24.78\%$ ($496$ одобренных заявок).
- **Динамика Approval Rate:** $-8.04$ п.п.
- **Матрица переходов решений (Net Approval Impact):**
  * Переходы в одобрение (`REJECT` $\to$ `APPROVE`): $+112$ заявок;
  * Потери одобрения (`APPROVE` $\to$ `REJECT`): $-273$ заявки;
  * **Чистый баланс (Net Impact):** $-161$ заявка (выявлено существенное ужесточение кредитной стратегии).
- **Результаты автоматических проверок:** сработало $27$ предупреждений (`FAIL`), локализовавших падение Approval Rate по 5 кредитным продуктам (`12412`, `15210`, `5123`, `751`, `91741`), отключение стоп-факторов и изменения атрибутного состава.

### Метрики производительности (по логам конвейера и профилированию):
- **Этап `load` (валидация структуры и инициализация прогона):** $0.006$ с ($6$ мс, `01:03:43.378` $\to$ `01:03:43.384`).
- **Этап `normalize` (парсинг $4004$ JSON, сравнение $290\,842$ строк, расчёт `pivot_facts` и пакетная запись в БД):**
  * Чистое время расчёта в памяти (Python / Pandas): $\sim 42.5$ с;
  * Сквозное время с записью в SQLite внутри контейнера: от $71.08$ с (`run_id: 1`) до $340.15$ с ($5$ мин $40$ с в `run_id: 2`, `01:03:43.396` $\to$ `01:09:23.551` с учётом синхронизации дискового тома Docker).
- **Этап `checks` (выполнение пакета проверок через `MartAPI` с сохранением в БД):** $5.18$ с (`01:09:23.568` $\to$ `01:09:28.753`; чистый расчёт в памяти — $0.85$ с).
- **Генерация экспертного AI-резюме (`RiskCopilot`):** $< 0.05$ с.
- **Генерация автономного HTML-отчёта (`html_generator.py`):** $0.32$ с.
- **Отклик сводной таблицы (Pivot) и смена раскладки в браузере:** $< 0.1\text{–}0.2$ с.

## 8. Ограничения и направления развития

### Выявленные узкие места и реализованные оптимизации
- **Главное узкое место:** построчный цикл `iterrows()` в Pandas при сопоставлении $290\,842$ строк витрины и поштучная вставка записей в БД — на первых итерациях на это уходило более $80\%$ времени прогона (несколько минут только на расчёт и десятки минут на запись).
- **Что дало кардинальное ускорение:**
  1. *Векторизация Pandas:* замена циклов `iterrows()` на векторные операции `np.select` и `.astype(str).fillna()` сократила этап сопоставления срезов до $10\text{–}15$ секунд.
  2. *Пакетная запись в БД:* использование `db.bulk_save_objects()` батчами по $10\,000$ строк вместо поштучного `db.add()` сократило запись $290\,842$ строк с десятков минут до нескольких секунд (при запуске в Docker на Windows/WSL2 основное время шага `normalize` приходится на дисковый I/O виртуализованного тома).
  3. *Предрасчёт агрегатов (`PivotFacts`):* генерация готовых фактов `counts` на этапе пайплайна позволила отдавать данные для сводной таблицы за $< 0.1$ с вместо выполнения тяжёлого `GROUP BY` по $290\,842$ строкам при каждом клике пользователя.
  4. *HTML-экспорт на стороне бэкенда с компактизацией:* генерация отчёта через Python со свёрнутыми превью длинных списков `APP_ID` избавила браузер от рендеринга $290\,000$ DOM-элементов и снизила вес HTML-файла с $35$ МБ до $1.8$ МБ.

### Текущие ограничения и направления дальнейшего развития
1. **Многопроцессорный парсинг JSON:** распараллеливание чтения и нормализации $4004$ файлов через `ProcessPoolExecutor` позволит сократить шаг `normalize` до $5\text{–}10$ секунд.
2. **Колоночная аналитическая СУБД:** переход с файловой SQLite на DuckDB или ClickHouse снимет накладные расходы дискового I/O при параллельной записи десятков прогонов объёмом от $20\,000+$ заявок.
3. **Прямая интеграция с корпоративными LLM:** подключение API больших языковых моделей к модулю `ai_summary.py` для интерактивного диалога аналитика с результатами прогона.
