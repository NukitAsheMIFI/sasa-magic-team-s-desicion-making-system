## 1. Описание решения
Многопользовательский веб-сервис для автоматизированного аудита и сравнения двух версий кредитных стратегий СПР: базовой `BEFORE (MASTER)` и тестовой `AFTER (BETA)`.

Сервис позволяет аналитикам и риск-менеджерам в сжатые сроки выявить влияние доработок на поток кредитных заявок:
- Формирует агрегированный бизнес-вердикт и отслеживает сдвиги в одобрении (Approval Rate, критические смены решений APPROVE / REJECT).
- Автоматически классифицирует расхождения по 4 типам изменений: `changed` (изменилось), `appeared` (появилось), `disappeared` (исчезло), `same` (совпало).
- Предоставляет интерактивную сводную таблицу (Pivot) с возможностью сквозной детализации (drill-down) от показателя до конкретной заявки и атрибута.
- Исполняет комплекс автоматических проверок (PASS / FAIL) с поддержкой добавления пользовательских правил на Python.
- Предоставляет выгрузку отчёта в HTML со ссылками для бесшовного перехода обратно в веб-приложение.

## 3. Используемые технологии
- **Бэкенд:** Python 3.11, FastAPI, Uvicorn, SQLAlchemy, Pandas.
- **База данных:** SQLite3 в режиме `WAL` (Write-Ahead Logging) для параллельного чтения и записи без блокировок интерфейса.
- **Фронтенд:** React 18, Vite, React Router, компонент интерактивной сводной таблицы (Pivot), встроенный редактор кода `@uiw/react-codemirror`.
- **Исполнение пользовательского кода:** изолированный запуск Python-процедур через `subprocess` и динамическую загрузку модулей (`importlib`).
- **Инфраструктура:** Docker, Docker Compose (единый контейнер со сборкой статики фронтенда через Multi-stage build), Bash.

## 4. Данные
- **Источник:** выданный датасет `src/data/RUN-20260827-0001/`, содержащий ответы СПР по **2002 кредитным заявкам** в двух срезах:
  * `BEFORE_MASTER` — 2002 JSON-файла (текущая промышленная версия стратегии);
  * `AFTER_BETA` — 2002 JSON-файла (тестируемая версия с изменениями).
  Суммарный объём выборки — 4004 файла (~20 МБ).
- **Структура входа:** имя файла соответствует идентификатору заявки (`APP_ID`) и выступает ключом сопоставления между срезами. Каждый ответ содержит от 131 до 178 атрибутов с вложенными структурами и массивами.
- **Этапы предобработки и приведения:**
  1. *Нормализация:* парсинг и «сплющивание» иерархических JSON-ответов в плоские таблицы с фиксацией пути атрибута (`attr_path`), значения, типа данных и глубины вложенности.
  2. *Вертикальный UNION:* объединение плоских срезов с сохранением признака источника (`SOURCE: BEFORE / AFTER`).
  3. *Сопоставление (Diff):* попарное сравнение атрибутов по ключу `(APP_ID, attr_path)` с разметкой 4 типов изменений и формированием детальной витрины (~290 000 строк).
  4. *Агрегация:* группировка по измерениям и расчёт предрассчитанных фактов `counts` (количество заявок в каждой группе) для сводного отчёта.

## 5. Архитектура и подход
1. **Асинхронный конвейер (Pipeline):**
   - Запуск расчёта выполняется в фоновом потоке, не блокируя основной веб-сервер.
   - Каждый алгоритмический этап (`normalize` → `compare` → `aggregate` → `checks`) логируется в таблице `run_steps` со сменой статусов (`queued` → `in_progress` → `done` / `error`).
   - Из журнала этапов пользователь может перейти к исходному коду процедуры, которая исполнялась на данном шаге.
   - Состояние прогона сохраняется в БД, благодаря чему интерфейс корректно восстанавливает прогресс и результаты после перезагрузки страницы (F5).
2. **Двухуровневая схема хранения:**
   - *Слой быстрых агрегатов (`counts` и `segments`):* используется для мгновенного построения и смены раскладки сводной таблицы в браузере без пересчёта 290 тысяч строк на каждый клик.
   - *Слой детальной витрины (`diffs` / `mart_rows`):* запрашивается точечно по индексам при переходе пользователя (drill-down) к конкретной заявке или атрибуту.
3. **Подключение процедур и проверок через конфигурацию:**
   - Приложение не привязано жёстко к структуре конкретного датасета: логика разбора вынесена в подключаемые процедуры по единому контракту входов и выходов.
   - Пользователь может выбрать готовый файл `.py` из файловой системы либо написать/скорректировать код процедуры и проверки прямо в интерактивном веб-редакторе.

## 8. Ограничения и направления развития

### Выявленные узкие места и оптимизации (шаблон по результатам замеров)
- **Главное узкое место:** `[ВСТАВИТЬ ОПИСАНИЕ, например: чтение и парсинг 4004 JSON-файлов с диска в один поток / вставка ~290 тыс. строк витрины в SQLite]`, на которое пришлось `[ВСТАВИТЬ % или ВРЕМЯ, например: ~80% времени прогона (XX сек)]`.
- **Что дало ускорение:**
  * Замена построчного сохранения в БД на пакетную транзакцию (`bulk_save_objects` + единый `commit`), что сократило запись с `[БЫЛО, например: X мин]` до `[СТАЛО, например: X сек]`.
  * Вынос рендеринга сводной таблицы на предрассчитанную таблицу `counts` (сократило отклик интерфейса на 290 тыс. строк с `[БЫЛО, например: X сек]` до `[СТАЛО, например: < 0.5 сек]`).

### Текущие ограничения
- **Хранилище SQLite:** отлично справляется с объёмом в тысячи заявок в рамках одного контейнера, но при одновременной записи десятков параллельных прогонов может возникать конкуренция за блокировку файла БД.
- **Выполнение на одном узле:** запуск пользовательских скриптов через `subprocess` ограничен вычислительными ресурсами одной машины.
- **Безопасность и версионирование:** в рамках MVP не реализованы песочница с жёсткими квотами памяти (cgroups) для пользовательского Python-кода и история версий редактируемых скриптов.

### Направления дальнейшего развития
1. **Параллелизация разбора:** распараллеливание парсинга JSON-файлов по ядрам CPU через `multiprocessing` / `ProcessPoolExecutor` (ожидаемое ускорение этапа нормализации в `[X–Y]` раз).
2. **Масштабирование хранилища и очередей:** переход на PostgreSQL / ClickHouse (или встраиваемый DuckDB для аналитических запросов) и вынос фоновых задач в очередь `Celery + Redis`.
3. **Инкрементальная догрузка:** обработка только новых или изменившихся заявок при догрузке очередного батча данных в существующий прогон без полного пересчёта.
4. **AI-ассистент («второе мнение»):** генерация автоматического текстового резюме по сдвигам метрик и причинам провала проверок с помощью LLM.
